## Decision boundary

At this snapshot, **#48 is closed; the other 14 issues are open**. No additional issue has a complete enough evidence packet to recommend immediate closure. That is not a recommendation to wait for every model call: most remaining issues have independently testable contracts.

- **#55 explicitly requires the 5,372-page migration.** #43, #50 and #56 aggregate the migration/release outcome through their component scope or dependencies.
- **#44–#47, #49, #51–#54 do not require all 5,372 pages to finish before their own scoped acceptance can be evaluated.** In particular, representative real-format ingestion can satisfy #52's format contracts independently of #55's all-page gate; #53 and #54 can use bounded published sources and separate isolated test state.
- Issue bodies define the deliverable. Later comments record missing evidence and failures; they do not silently add a requirement for a particular renderer, a whole-corpus quality benchmark to every component, or a specific UI interaction not stated in the body.
- Passing mocked/unit tests proves the tested contract, not a real upstream response or browser interaction. Conversely, a deterministic fault need not be induced against a paid external account: an isolated HTTP fault proxy can test the deployed boundary and must be labelled as injected fault evidence.
- Closing a component is not production release approval, nor permission to delete old sources/indexes/logs.

Current evidence mapping:

2. **Scope/publication/review: real partial plus focused contract tests.** Positive 21.1/21.3/module and negative version/module/Solution/language/environment/foreign actor are recorded. Include a small published/unpublished/deprecated/conflicting set and positive scope fixture in the final packet; do not conflate negative Solution evidence with positive labelled material.
3. **Faults: unit pass; partial runtime pass.** `tests/weknora.test.ts` injects fetch timeout/429/401/503/invalid JSON; `tests/weknora-protocol.test.ts` rejects malformed envelopes, foreign chunks and invalid summary citations. Actual engine stop/start has real HTTP/MCP evidence. The remaining matrix can run through an isolated real HTTP boundary with an explicitly labelled fault proxy. It need not disrupt the active engine or deliberately exhaust the paid provider.
4. **Privacy: source regression pass; deployment-window evidence pending.** `tests/knowledge-retrieval-privacy.test.ts` (3), `tests/request-log-privacy.test.ts` (4) and `tests/retrieval-tool-audit.test.ts` (3) verify new metadata-only writes, raw request preservation, ContextPack expansion, 404 and malformed-JSON logs. Send unique synthetic query/header/body/error sentinels through actual HTTP and MCP, then scan only the new telemetry/log window; assert response content and retrievalRunId/reuse association are preserved. Include actual tools/call audit, not just the helper function.
5. **Bilingual/object/path/version/conflict cases: fixture exists; live scores incomplete.** The 29-case five-source fixture is independent of the full corpus. Select a declared subset of real published sources; report every attempted/failed/not-ready case. Chinese wording around an English object tests a Chinese query, not a native Chinese document. The separate full-corpus FTS path failure is not proof of engine path failure or success.

A component closure packet can therefore remain small. It must not claim global gold-set quality, true upstream 429 issuance, or absence of historical leakage. Historical retention/remediation remains explicitly governed by [the privacy policy](retrieval-telemetry-privacy.md); deleting it is not an implicit prerequisite or permission from this audit.

## #54: exact requirements versus inferred improvements

Exact **page capabilities** from [#54](https://github.com/tengfei1994/Relay-MCP/issues/54):

> Product Knowledge：知识库/版本/模块/语言/状态筛选、上传、解析进度、失败详情、重新解析、发布和弃用。

> Document detail：标题层级、表格、代码、来源路径、anchor、引用、chunk、parser version、source hash 和版本绑定。

Exact **acceptance criteria**:

> 管理员可以在 Relay 页面上传 HTML/Markdown/规范化 CHM 内容并查看完整导入进度。

> 通过浏览器/API、分页、刷新恢复、权限、引用跳转、diff 和敏感字段测试。

The other four criteria explicitly require Wiki search/source opening, audited edit/publish/deprecate/rollback without changing Confirmed Memory lifecycle, foreign-scope denial, and recoverable engine-down UI preserving Memory/Evidence/tools.

### What the current UI actually supplies

- `KnowledgeProduct.tsx` `ProductImport` has file selection for `.md/.markdown/.html/.htm/.pdf/.zip`, upload sessions, asynchronous job polling and a localStorage job ID for refresh recovery. Normalized CHM can be an HTML/Markdown file. **Lack of a raw `.chm` picker is not a failure of the stated normalized-CHM acceptance criterion.**
- `KnowledgeIntegrated.tsx` has server-side `limit/offset` pagers for Product-engine documents and Wiki, explicit source scope, staged readiness/chunk/model metadata and Publish/Deprecate controls. Its Migration pane has `Retry failed migration`.
- Product detail exposes source/hash/version and section text/anchor; the inspected `KnowledgeProduct.tsx` has no explicit parserVersion/revisionId rendering. Parser version and version binding are named capabilities; revisionId itself is a possible implementation of binding display, not a prescribed field name.
- Section text is displayed in a whitespace-preserving paragraph. This does not yet prove that users can understand source table row/column relationships and code indentation, but the issue does **not prescribe a Markdown library, HTML renderer or syntax highlighting**. A browser structure/readability test should establish the capability before selecting implementation.

### Do not inflate the closing gate

- **Native image rendering is not stated in #54.** Preserving source image references is explicit in #42/#52, and serving clickable original assets is a separate source-reader quality concern. A native image viewer is a product suggestion, not a newly mandatory #54 gate.
- **Per-document reparse is not stated.** “重新解析” is a named page capability, and the latest acceptance comment asks for failure/reparse evidence. A batch operation can satisfy it if the UI demonstrably invokes the formal parse/retry operation and records progress/result; merely refreshing status or retrying an already accepted ID is not automatically reparse proof. Audit the existing migration retry semantics before adding a new button.
- **No all-corpus embedding threshold is stated.** An isolated page-boundary dataset is enough to exercise pagination/loading limits. Do not present fabricated entries as real Product evidence; label the paging fixture.
- **No need to repeat completed Candidate Review acceptance.** #48 remains a separately closed component.

Suggested independent automation: upload one genuine small HTML, one Markdown and one approved normalized CHM excerpt through the actual browser; observe durable job progress after refresh; introduce a safe invalid input in isolated state, inspect failure and a supported retry/reparse; explicitly publish then deprecate; inspect detail/parser/source/hash/binding; exercise two list pages and filters; repeat with foreign actor/environment; capture only metadata and scan new logs/network/storage for synthetic sentinels. Reuse existing Wiki lifecycle/outage evidence when the deployed build and relevant code are unchanged, otherwise repeat only affected checks.
