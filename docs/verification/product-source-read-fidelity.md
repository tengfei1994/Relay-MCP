# Product source-read fidelity

The browser acceptance of a published CHM document exposed duplicate headings, anchors and tables. Relay had reconstructed the document body by joining indexed chunks, which contain overlap and can split table and code syntax. Correct stored upload bytes and correct individual chunks did not establish a faithful full-document read.

The repair reads `GET /api/v1/knowledge/:id/download` from the configured internal WeKnora base URL using the existing API-key/JWT transport. It does not follow URLs in document metadata, use a downloaded filename as a filesystem path, or follow HTTP redirects. The download-specific `redirect: manual` and binary Accept header leave other API requests unchanged. No upstream API or engine patch is added.

The verified upstream contract is WeKnora v0.8.3, source commit `3e22822c1d2397be730c458c7539d0eb8c113a24`: [route and access guards](https://github.com/Tencent/WeKnora/blob/3e22822c1d2397be730c458c7539d0eb8c113a24/internal/router/routes_knowledge.go#L138), [download handler](https://github.com/Tencent/WeKnora/blob/3e22822c1d2397be730c458c7539d0eb8c113a24/internal/handler/knowledge.go#L1987), and [original-file service](https://github.com/Tencent/WeKnora/blob/3e22822c1d2397be730c458c7539d0eb8c113a24/internal/application/service/knowledge.go#L791). The source was inspected read-only in the pinned nonproduction build. The service returns the saved upload file stream (or manual document content), not reconstructed chunks.

For Relay's Product documents, that original upload is normalized Markdown. The client requires a complete HTTP 200 response, retains the existing timeout and 16 MiB response limit, verifies the expected SHA-256 of the exact downloaded bytes when supplied, and decodes strict UTF-8 without dropping a BOM or changing newlines. Product reads always supply the published mapping's normalized SHA and recheck both the current mapping hash and returned body after the network wait. Invalid/missing hashes, changed source bytes, download errors, partial responses and invalid UTF-8 fail closed. There is no fallback to chunk concatenation or Relay's local body.

Document metadata, chunk pagination, allowed chunk references, publication/current-KB filtering and the post-request ACL checks remain in place. The read DTO still returns document metadata, `content` and `chunks`; Product `body` and summary now derive from the original source, while citations and sections remain actual indexed chunks.

Tests use an isolated loopback HTTP server and the real client to cover overlapping chunks and a table/code block split across chunk boundaries, authenticated fixed download paths, untrusted URL/filename metadata, 301/302/307/308 redirects with zero requests to the target, 401/404/500/204/206 failures, incorrect SHA, invalid UTF-8, BOM/CRLF preservation and the response size limit. Product tests separately cover mandatory hash forwarding, corrupted injected-client content, mapping changes during the request and ACL revocation. Protocol/catalog fixtures now serve the official download response and matching hashes instead of assuming joined chunks are the source.

The new regression cases failed against the old implementation before the source change. These are client and boundary contract checks with synthetic source text, not a claim of browser or live engine acceptance. They make zero cloud-model calls and do not change active databases, engine configuration, binaries or corpus evidence. Live CHM browser readback remains a separate deployment acceptance step.

That deployment step subsequently passed on archive `6fe51ed5a6d5e08aaf0f913918d29156c2b5138f8f2034c4a00f60aec2a47b0e`: two genuine CHM bodies and the Wiki source matched their complete normalized SHA-256 values, with 32 verified citations. Real browser tables/code/headings/unique anchors and the Wiki-to-source jump were checked. Full metadata and the dedicated CHM deprecation boundary are recorded in [the final acceptance checkpoint](knowledge-acceptance-20261026.md); source report SHA is `c4b6aa3de6cf9ba6d1bc11aac8c54d6890a4e4dbfe9e1d8c80e0d80a7a3e2ce9`.
